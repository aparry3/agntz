# Agntz gaps for hosting Nutritext AI calls

Status: implemented in the working tree as of July 28, 2026

## Implementation status

The migration-critical path described in this audit is now implemented:

| Gap | Implemented contract |
|---|---|
| Recursive JSON Schema | Draft 2020-12 object-root schemas, legacy shorthand migration, bounded validation, and provider forwarding |
| Model settings | Common AI SDK settings plus provider-scoped `providerOptions` |
| Multimodal hosting | Ordered text/image blocks, per-image detail, URL/base64/artifact inputs, and client-side local-file upload |
| Transcription | `kind: transcription` using the same run APIs and managed audio artifacts |
| Hosted business tools | Typed `kind: callback` tools with trusted runtime context, HMAC signatures, stable delivery IDs, and bounded retries |
| Result metadata | Sync results now include run/version/provider/model/usage/finish metadata |
| Retention | `none`, redacted `result`, and conversational `session` modes with independent run/artifact TTLs |
| Image generation | `kind: image` with generated bytes stored as expiring output artifacts |

The TypeScript and Python hosted clients share
`contracts/hosted-client-parity.json` as a release gate. Existing manifests are
additively migrated: the legacy property-map schema shorthand remains accepted,
while newly authored manifests can use canonical JSON Schema directly.

Embeddings, speech synthesis, moderation, realtime, and provider batch APIs
remain future operation adapters rather than public manifest kinds. They are
not required by the Nutritext call inventory in this document.

## Purpose

Nutritext currently makes several non-batch OpenAI and Anthropic requests
directly. The goal is to replace the provider-specific request at each call site
with an Agntz hosted-agent invocation so that the agent's prompt, model,
structured-output schema, and model settings can be changed in Agntz without a
Nutritext deployment.

This document describes only the capabilities missing from Agntz that prevent
or complicate that substitution. It does not propose moving Nutritext business
logic into Agntz.

Anthropic Message Batch API requests are deliberately out of scope.

## Version boundary

Nutritext currently declares:

- `@agntz/client` `0.0.0` in the web application.
- `@agntz/sdk` `0.0.0` and `@agntz/stores` `0.0.0` in the SMS service.

The audit also compared those packages with the sibling Agntz repository at
commit `09ee024` as it existed locally on July 28, 2026. That checkout contained
uncommitted release work. In particular, the structured-schema validation issue
described below should be checked against the exact version deployed to
agntz.co before making changes.

## The intended integration boundary

The desired request flow is:

```text
Nutritext prepares an input
        |
        v
Nutritext calls a hosted Agntz agent
        |
        v
Agntz loads the active manifest version
        |
        v
Agntz calls the configured model
        |
        v
Agntz returns structured output and request metadata
        |
        v
Nutritext validates, interprets, budgets, caches, and persists the result
```

The one-time Nutritext change is replacing a direct provider call with an Agntz
client call. After that change, these should be editable in Agntz without
changing Nutritext:

- System instructions and examples.
- The provider and model.
- Model sampling and reasoning settings.
- Maximum output tokens.
- The structured-output schema, as long as it remains compatible with the
  Nutritext contract consuming it.
- Tool descriptions and model-visible tool input schemas.

These remain Nutritext responsibilities:

- Selecting which records need AI processing.
- Chunking records into appropriately sized requests.
- Downloading and preprocessing social media.
- Choosing and labeling video frames.
- Deterministic ingredient parsing and selecting its unresolved residue.
- User authorization and database access.
- Validating model output against application invariants.
- Mapping output back to source records.
- Calculating cost and enforcing application budgets.
- Caching, invalidation, retries, and database persistence.

Changing the *shape* of an application contract can still require Nutritext
code. For example, adding a new recipe facet can require a database migration,
Zod changes, TypeScript changes, and persistence changes even if the model
schema is hosted in Agntz. The no-code promise applies to agent behavior within
an existing application contract.

## Current AI call inventory

| Call | Current transport | Agntz state |
|---|---|---|
| Recipe search intent | Hosted Agntz agent | Already migrated |
| User profile parsing | Hosted Agntz agent | Already migrated |
| Recipe facet enrichment | Direct Anthropic Messages API | Close to migratable |
| Ingredient residue parsing | Direct Anthropic Messages API | Close to migratable |
| Social narration transcription | Direct OpenAI multipart transcription API | Not currently representable |
| Social visual recipe extraction | Direct OpenAI Responses API with text and images | Not currently equivalent |
| SMS nutritionist | Embedded Agntz SDK with local tools | Works locally, but not equivalently as a hosted agent |
| Image generation | Not currently used | No first-class Agntz capability |

The following sections explain the Agntz gaps behind those classifications.

## Gap 1: manifests do not consistently support the required JSON Schema

### How Nutritext does it now

Facet enrichment sends Anthropic a structured-output schema through
`output_config.format`:

```ts
await llm.messages.create({
  model,
  max_tokens: maxTokens,
  system: SYSTEM_PROMPT,
  output_config: {
    format: {
      type: "json_schema",
      schema: OUTPUT_SCHEMA,
    },
  },
  messages: [/* recipe JSON */],
});
```

See:

- `packages/enrichment/src/facets.ts`
- `packages/enrichment/src/payload.ts`
- `packages/enrichment/src/taxonomy.ts`

The schema contains a top-level array of recipes and nested objects, arrays,
enums, required properties, and booleans.

Ingredient residue parsing uses the same Anthropic structured-output mechanism
with an output resembling:

```json
{
  "lines": [
    {
      "index": 0,
      "qty": 2,
      "unit": "tablespoon",
      "food": "olive oil",
      "optional": false
    }
  ]
}
```

Its schema includes nullable unions such as:

```yaml
qty:
  type: [number, "null"]
```

See `scripts/nutrition/estimate.mjs`.

Social extraction uses OpenAI strict structured output through
`text.format.schema`. It has the deepest schema of the current calls: recipe
metadata, ingredient evidence, equipment, timing, confidence, missing details,
and frame references.

See `scripts/social-recipe/pipeline.mjs`.

### Why Agntz cannot be substituted confidently today

Agntz's manifest types describe input and output fields primarily as flat
property definitions. Parts of the manifest-to-agent conversion code accept
nested JSON Schema fragments, but the current strict validator rejects or does
not type standard nested fields consistently, including:

- `properties`
- `items`
- `required`
- `additionalProperties`
- union-valued `type`, such as `[string, "null"]`
- standard numeric constraints such as `minimum` and `maximum`

Relevant Agntz source areas:

- `packages/core/src/manifest/types.ts`
- `packages/core/src/manifest/validate.ts`
- `packages/core/src/manifest/manifest-to-agent.ts`
- `packages/core/schema/agent-manifest.schema.json`

This is also inconsistent with Nutritext's two existing hosted manifests:

- `agents/recipe-search-intent.yaml`
- `agents/user-profile.yaml`

Those manifests already use arrays, `items`, and nullable union types. An older,
more permissive Agntz validator may be why they imported successfully, while
the current release-prep validator would reject equivalent new imports.

Without a reliable manifest schema contract, Nutritext cannot move the facet,
nutrition, or social schemas into Agntz and trust that the hosted agent is
enforcing the same output contract as the direct provider request.

### Agntz capability requested

Treat manifest input and output schemas as real, recursively validated JSON
Schema fragments rather than flat field descriptors.

At minimum, the supported subset needs:

- Objects and nested `properties`.
- Arrays and nested `items`.
- `required`.
- `additionalProperties`.
- String, number, integer, boolean, object, array, and null types.
- Nullable type unions.
- `enum`.
- `minimum`, `maximum`, and normal string/array constraints when the underlying
  model SDK supports them.

The manifest parser, TypeScript types, generated manifest schema, runtime
validator, and provider conversion should all accept the same subset.

### Definition of done

1. The existing recipe-search and user-profile manifests validate.
2. The facet, nutrition-residue, and social-extraction schemas can be copied
   into manifests without weakening or flattening them.
3. The provider receives an equivalent structured-output schema.
4. Invalid nested schema constructs fail at manifest validation time with a
   useful path and message.
5. Provider-harness tests cover both OpenAI and Anthropic with nested arrays,
   objects, enums, and nullable fields.

### What stays in Nutritext

Nutritext still:

- Parses the returned object.
- Rejects invented or unmatched IDs.
- Detects missing rows.
- Applies Zod and semantic validation.
- Converts valid answers into database patches.
- Decides whether the schema change requires an application or database
  migration.

## Gap 2: manifest model settings are not faithfully applied

### How Nutritext does it now

Direct provider requests explicitly configure the settings relevant to each
call.

Facet enrichment configures:

- Anthropic model.
- Maximum output tokens.
- Structured-output schema.

Ingredient residue parsing configures:

- Anthropic model.
- `max_tokens: 8000`.
- Structured-output schema.

Social visual extraction configures:

```json
{
  "model": "gpt-5.6-luna",
  "store": false,
  "reasoning": {
    "effort": "medium"
  },
  "text": {
    "verbosity": "low"
  }
}
```

Every social image also has an image-detail setting, normally `high`.

The existing hosted recipe-search and user-profile manifests declare
`temperature: 0`. The embedded nutritionist manifest declares
`temperature: 0.7`.

### Why Agntz cannot be substituted equivalently today

Agntz exposes some settings in its manifest model configuration, but the
current model-provider adapter calls `generateText` and `streamText` without
forwarding at least `temperature` and `topP`.

Relevant Agntz source:

- `packages/core/src/model-provider.ts`

As a result, a manifest can appear to configure deterministic temperature-zero
behavior while the provider receives its default temperature.

The manifest also lacks a general, validated way to express provider-specific
settings needed by the social call:

- OpenAI reasoning effort.
- Text verbosity.
- Provider-side `store: false`.
- Image detail or an equivalent per-image setting.

This is a configuration fidelity problem. If the manifest cannot fully
describe the provider invocation, changing the manifest is not an equivalent
replacement for changing the direct request in Nutritext.

### Agntz capability requested

Support two layers of model options:

1. Provider-neutral settings that Agntz forwards directly, such as
   temperature, top-p, maximum output tokens, timeout, and possibly seed.
2. Provider-scoped settings for features that do not have a safe universal
   abstraction.

One possible manifest shape is:

```yaml
model:
  provider: openai
  name: gpt-5.6-luna
  maxTokens: 16000
  temperature: 0
  providerOptions:
    openai:
      reasoningEffort: medium
      textVerbosity: low
      store: false
      imageDetail: high
```

The exact shape is less important than ensuring that:

- unsupported options fail clearly;
- provider-specific options are namespaced;
- secrets cannot be embedded accidentally;
- the options actually reach the provider SDK.

### Definition of done

1. A provider-harness test verifies that temperature and top-p reach OpenAI and
   Anthropic.
2. The social agent can configure reasoning effort, verbosity, provider
   storage, and image detail without Nutritext request code.
3. The resolved settings appear in trace or run metadata so a run can be
   audited.
4. Existing manifests that omit the new options retain provider defaults.

### What stays in Nutritext

Nutritext decides which agent to call and supplies its application input. It
does not need to understand the active model settings after migration, except
when it uses returned model/usage metadata for cost accounting.

## Gap 3: hosted manifest execution does not preserve multimodal input

### How Nutritext does it now

The social pipeline:

1. Downloads the post and metadata.
2. Extracts narration audio and samples up to 36 frames.
3. Transcribes the narration.
4. Builds one ordered OpenAI user message containing:
   - Post metadata and caption.
   - Narration transcript.
   - A label for the platform thumbnail.
   - The thumbnail image, if present.
   - A text label containing each frame's index and timestamp.
   - The corresponding image immediately after each label.
5. Sends the message to the vision-capable model.

The order is meaningful. A model must see:

```text
FRAME 12 at 18.40 seconds:
[the image for frame 12]
```

not a JSON dump containing unrelated text and base64 fields.

See `requestRecipeExtraction` in
`scripts/social-recipe/pipeline.mjs`.

### Why Agntz cannot be substituted today

The Agntz client and core contracts already define text/image content blocks,
and the core runner understands multimodal messages.

The hosted manifest path does not preserve that representation:

1. The worker passes the original input to manifest execution.
2. Manifest state creation treats a non-string input without an input schema as
   `String(input)`.
3. An array of content blocks therefore becomes a string similar to
   `[object Object],[object Object]`.
4. If an input schema is added, the blocks become ordinary state/JSON rather
   than ordered provider message parts.
5. The manifest execution bridge then invokes the LLM with a string.

Relevant Agntz source:

- `packages/client/src/types.ts`
- `packages/core/src/manifest/state.ts`
- `packages/core/src/manifest-execution-context.ts`
- `packages/worker/src/routes.ts`

The public client surface therefore suggests hosted multimodal support that the
hosted manifest executor does not actually preserve.

### Agntz capability requested

Allow a hosted LLM agent to receive `ContentBlock[]` as its raw user message.
The manifest should still supply the system instruction, output schema, model,
and provider options, but it must not stringify the content blocks.

The runtime also needs explicit composition rules:

- If input is a string or structured application object, the manifest prompt
  template may render it normally.
- If input is `ContentBlock[]`, it becomes the ordered user message.
- If a manifest needs to prepend a rendered text prompt to content blocks,
  Agntz should define an explicit mechanism rather than implicitly serializing
  them.

### Definition of done

1. A hosted agent receives alternating text and image blocks in the exact order
   supplied by the client.
2. URL images and base64 images both work.
3. A provider-harness assertion confirms the provider adapter receives native
   image parts rather than JSON or `[object Object]`.
4. The social extraction schema can be used simultaneously with multimodal
   input.
5. Per-image or manifest-default detail is supported.
6. Abort signals still cancel the provider request.

### What stays in Nutritext

Nutritext continues to:

- Download the post.
- Choose the number and timestamps of frames.
- Read image files or upload them as artifacts.
- Label thumbnails and frames.
- Construct the ordered content blocks.
- Validate evidence references in the returned recipe.
- Choose and upload the cover image.

Agntz is only responsible for preserving the model message and executing the
configured agent.

## Gap 4: no hosted audio/transcription input

### How Nutritext does it now

Nutritext uses FFmpeg to extract an MP3 from the downloaded social video. It
then sends that local file to OpenAI's transcription endpoint as multipart form
data:

```text
file=<audio bytes>
model=gpt-4o-transcribe
response_format=json
prompt=Cooking video narration. Preserve ingredient amounts, units,
       temperatures, and times exactly.
```

See `transcribeAudio` in `scripts/social-recipe/pipeline.mjs`.

Nutritext consumes the returned transcript as plain text and supplies it to the
later visual recipe-extraction call.

### Why Agntz cannot be substituted today

Agntz currently models LLM execution around text generation and streaming text
generation. Its content blocks support text and images, not audio or general
files. Its declarative HTTP tools do not provide a complete multipart/binary
upload path suitable for a provider transcription request.

Consequently, Nutritext cannot send the extracted MP3 to a hosted
transcription agent while moving the model, prompt, and transcription settings
into a manifest.

### Agntz capability requested

Agntz needs a first-class way to transport files to a hosted model operation.
Two reasonable designs are:

1. An audio/file content block supported by compatible models.
2. An uploaded Agntz artifact reference consumed by a `transcription` agent
   kind or model capability.

For example:

```yaml
id: social-narration-transcription
kind: transcription
model:
  provider: openai
  name: gpt-4o-transcribe
settings:
  responseFormat: json
instruction: |
  Preserve ingredient amounts, units, temperatures, and times exactly.
```

The client could then upload or reference the MP3 and receive transcript text
plus run metadata.

An artifact design is preferable to embedding large base64 audio in every JSON
request. It should define MIME type, size limits, expiry, ownership, and
retention.

### Definition of done

1. Nutritext can provide an `audio/mpeg` file without constructing a
   provider-specific multipart request.
2. The model and transcription prompt are selected by the active manifest.
3. The result contains transcript text and token/duration/cost metadata
   available from the provider.
4. Temporary audio is not retained indefinitely unless the caller explicitly
   requests it.
5. Abort signals and file-size errors behave predictably.

### What stays in Nutritext

Nutritext still downloads the video, invokes FFmpeg, decides whether usable
audio exists, and passes the resulting transcript to social extraction.

## Gap 5: hosted tools cannot carry typed arguments and trusted runtime identity

### How Nutritext does it now

The SMS nutritionist already uses the Agntz SDK, but it runs embedded inside the
Nutritext service. Its manifest declares two local tools:

- `find_recipes`
- `save_recipe`

The implementations live in `service/src/lib/tools/index.ts`.

The tools have typed Zod inputs. For example, `find_recipes` accepts optional
strings, arrays, integers, and booleans:

```ts
{
  query?: string;
  tags?: string[];
  maxTimeMinutes?: number;
  maxCalories?: number;
  savedOnly?: boolean;
  limit?: number;
}
```

The user's identity does not come from model arguments. Nutritext creates one
session per user using the user's UUID as `sessionId`, and each tool derives the
user ID from trusted `ToolContext`:

```ts
execute: (args, ctx) => findRecipes(requireUserId(ctx), args)
```

This prevents the model from searching or modifying another user's recipes by
inventing a user ID.

### Why the hosted Agntz agent cannot replace it today

A hosted Agntz worker cannot execute arbitrary JavaScript callbacks inside the
Nutritext process. The business functions therefore need to remain in
Nutritext and be called remotely.

Agntz's current declarative HTTP tool is not sufficient for that boundary:

- Its model-visible input shape is mainly inferred from URL placeholders.
- Placeholder values are strings, which cannot faithfully express arrays,
  numbers, booleans, and nested objects.
- The request body is interpolated from initial agent state, not generally from
  the model's tool-call arguments.
- Trusted runtime values such as `sessionId`, user context, and run ID are not
  exposed to the callback body or protected headers.

Relevant Agntz source:

- `packages/core/src/http-tool.ts`
- `packages/core/src/runner.ts`

Passing `userId` as an ordinary model tool argument would be a security
regression and is not an acceptable workaround.

### Agntz capability requested

Agntz needs either a dedicated callback/webhook tool kind or a more capable
HTTP tool contract.

A callback invocation should carry:

```json
{
  "tool": "find_recipes",
  "args": {
    "tags": ["vegetarian", "quick"],
    "maxTimeMinutes": 30,
    "limit": 7
  },
  "runtime": {
    "sessionId": "trusted-session-id",
    "runId": "trusted-run-id",
    "agentId": "nutritionist"
  }
}
```

Required properties:

- The model-visible `args` use an explicit JSON Schema and retain their types.
- Trusted runtime properties are injected by Agntz after the model tool call.
- Runtime identity is not included in the model-visible tool schema.
- The request is authenticated, preferably with an Agntz-generated signature
  covering the body, timestamp, and delivery ID.
- Retries are idempotency-aware, especially for `save_recipe`.
- Callback failures return structured tool errors to the agent.

If this is implemented by extending HTTP tools, the manifest needs:

- An explicit tool `inputSchema`.
- `{{args.*}}` interpolation in JSON bodies.
- A protected `{{runtime.*}}` namespace.
- Typed JSON interpolation rather than string-only substitution.
- Signed headers or a first-class webhook secret.

### Definition of done

1. The hosted nutritionist can call `find_recipes` with typed optional
   arguments.
2. The callback can identify the Nutritext user from trusted runtime context.
3. The model cannot select or override another user's ID.
4. `save_recipe` can be retried without duplicate side effects.
5. Tool output returns to the same hosted agent run.
6. Nutritext's existing repository functions remain the implementations.

### What stays in Nutritext

Nutritext retains:

- User/session mapping.
- Authorization.
- `findRecipes` and `saveUserRecipe`.
- SQL and database transactions.
- Idempotency rules for saved recipe URLs.
- SMS scheduling and delivery.
- Cancel-and-replace handling for rapidly arriving messages.

Only the language-model loop and tool-call orchestration move to hosted Agntz.

## Gap 6: the synchronous run response omits metadata Nutritext currently uses

### How Nutritext does it now

Facet enrichment reads input and output token counts from every Anthropic
response. The crawler converts those counts to USD using its configured model
prices and records the spend before attempting database writes:

```text
provider call
  -> read actual token usage
  -> record billable spend
  -> validate and persist facet patches
```

See:

- `packages/enrichment/src/facets.ts`
- `crawler/src/lib/recipe-enrichment.ts`
- `worker/src/index.ts` for the legacy standalone path

Social extraction returns:

- The structured recipe.
- The resolved response model.
- Provider usage.

The production social worker persists the model and usage when marking the job
ready. See `crawler/src/social.ts`.

The provider response status is also checked before Nutritext treats the
structured result as successful.

### Why a simple Agntz substitution is awkward today

The current synchronous `agents.run()` result contains:

- `output`
- `state`
- `sessionId`
- optional replies

It does not contain the aggregate usage or resolved model that Nutritext's
existing code consumes.

Agntz's asynchronous run records already aggregate prompt, completion, and
total tokens and a model. Nutritext could use `runs.start()` followed by
polling `runs.get()`, so this is not an absolute execution blocker. It is,
however, no longer a straightforward transport replacement for a synchronous
provider call.

The simple result also does not consistently surface the resolved hosted agent
version. That version is useful when prompts and models can change without a
Nutritext deployment: a durable recipe should be traceable to the agent version
that classified it.

Relevant Agntz source:

- `packages/client/src/types.ts`
- `packages/worker/src/routes.ts`
- `packages/core/src/run-registry.ts`

### Agntz capability requested

Return a consistent result envelope for synchronous and asynchronous
invocations:

```ts
interface HostedAgentResult<T> {
  output: T;
  sessionId: string;
  runId: string;
  traceId?: string;
  requestedAgentVersion?: string;
  resolvedAgentVersion?: string;
  provider: string;
  model: string;
  usage: {
    inputTokens: number;
    outputTokens: number;
    totalTokens: number;
  };
  status: "completed";
  finishReason?: string;
}
```

Provider-specific response IDs are optional because Nutritext does not
currently persist the OpenAI response ID. Usage, model, completion status, and
the resolved Agntz version are the important pieces.

Refusal, incomplete, cancellation, and provider failure must not appear as a
normal completed structured result. They may be represented as typed errors or
non-completed statuses.

This does not ask Agntz to calculate Nutritext's budget or write Nutritext
records. It only asks the transport to report the metadata produced by the
model run.

### Definition of done

1. A synchronous hosted facet call returns aggregate input/output usage.
2. The returned model reflects the model actually used, not merely the
   requested default.
3. The result identifies the resolved agent version.
4. Sync and async APIs use the same usage field names or provide a lossless
   mapping.
5. Refused, incomplete, failed, and cancelled calls are distinguishable from
   successful structured output.

### What stays in Nutritext

Nutritext continues to:

- Maintain model pricing.
- Convert token usage to USD.
- Enforce its daily budget.
- Decide when spend is recorded.
- Decide whether and where to persist the agent/run version.
- Validate and persist the returned content.

## Gap 7: hosted runs have no caller-controlled retention mode

This is an operational platform gap, not a functional blocker for text-only
execution. It matters most for social extraction.

### How Nutritext does it now

The direct OpenAI social extraction request sets provider-side `store: false`.
Production media is processed in a temporary directory that is removed after
the job. Nutritext persists the resulting recipe and selected cover rather than
an extra provider conversation containing every base64 frame.

Facet and nutrition calls are also stateless classification operations. Every
chunk is independent and does not need conversation history.

### Why hosted Agntz changes the behavior

Hosted Agntz currently allocates a session for every run and persists session
messages. A social extraction request may contain a thumbnail and up to 36
base64 images. Persisting that full user message would create a materially
different retention and storage profile from the current direct call.

Setting OpenAI `store: false` through provider options controls provider-side
storage; it does not stop Agntz from persisting the request in its own session
and trace stores.

### Agntz capability requested

Add an explicit run retention policy, for example:

```ts
retention: "none" | "trace-only" | "session"
```

Possible semantics:

- `none`: execute without persisting input, output, session messages, or raw
  trace I/O; retain only minimal operational counters if required.
- `trace-only`: retain timing, usage, model, agent version, and status but redact
  or omit raw content and binary/base64 bodies.
- `session`: current conversational behavior.

Stateless classification agents should be able to choose a manifest default,
with callers allowed to request an equal or stricter policy.

### Definition of done

1. Facet and nutrition calls can run without accumulating conversational
   sessions.
2. Social traces can retain usage and timing without storing frame bytes.
3. The selected policy applies to both successful and failed runs.
4. Provider-side storage settings and Agntz-side retention are independently
   visible and configurable.

### What stays in Nutritext

Nutritext still decides which source media and derived artifacts it persists in
its own storage.

## Gap 8: no first-class image-generation operation

This is a future gap. Nutritext does not currently generate images with AI.

### Why the current Agntz abstraction is insufficient

Agntz's model-provider abstraction is centered on generated text, structured
text output, and streaming text. There is no first-class image-generation
operation or result artifact.

A generic HTTP tool could eventually call an image provider, but that would
not provide the main benefits expected from a hosted agent:

- Manifest-controlled image model and settings.
- A typed image result.
- Hosted artifact management.
- Provider usage and cost metadata.
- Image-generation traces and errors.
- Asynchronous generation lifecycle.

### Agntz capability requested

Add an image-generation agent kind or model capability with manifest settings
for:

- Provider and model.
- Prompt/instruction templating.
- Size and aspect ratio.
- Quality.
- Background/transparency.
- Number of outputs.
- Provider-specific options.

The result should use an artifact rather than an enormous base64 string:

```ts
interface GeneratedImageArtifact {
  artifactId: string;
  url?: string;
  mediaType: string;
  width?: number;
  height?: number;
  expiresAt?: string;
}
```

The run should also expose provider, model, usage/cost inputs, status, and
resolved agent version.

### Definition of done

1. A manifest fully configures an image-generation request.
2. The client receives one or more typed image artifacts.
3. Large generated bytes do not need to live in session JSON.
4. Async polling or callbacks work for long generations.
5. Retention and expiry are explicit.

### What stays in Nutritext

Nutritext would decide when an image is needed, construct the business-specific
input, review or moderate the output as required, and persist or display the
selected asset.

## What is explicitly not an Agntz gap

The following behaviors appeared during the audit but should not become Agntz
library requirements.

### Enrichment chunking and result mapping

`enrichFacets` divides rows into chunks, accumulates usage, matches answers by
UUID, reports missing/unmatched rows, and creates patches. Only its
`llm.messages.create(...)` transport should change.

Conceptually:

```ts
// Current
const message = await anthropic.messages.create(providerRequest);

// Target
const run = await agntz.agents.run({
  agent: "recipe-facet-enrichment",
  input: { recipes: chunk },
});
```

Everything around that call remains.

### Nutrition parser selection and caching

The deterministic parser decides which ingredient lines require model help.
The LLM parses only that residue. Nutritext maps results back by index/hash and
caches them. Agntz should not decide which lines qualify or how cache
invalidation works.

### Social-media processing

`yt-dlp`, FFmpeg, frame sampling, timestamp labels, post metadata normalization,
cover selection, evidence validation, nutrition estimation, and media cleanup
are application pipeline stages. Agntz receives the already prepared agent
input.

### Application validation

Agntz structured output guarantees shape. Nutritext semantic checks still
enforce rules such as:

- Returned recipe IDs must match requested IDs.
- A garlic amount inferred without a visible unit must be marked estimated.
- Evidence frame indices must refer to frames that were actually supplied.
- Required database invariants must hold.

These rules protect the application even if a model produces schema-valid but
incorrect content.

### Spending policy

Agntz needs to report usage. Nutritext remains responsible for:

- Model-specific prices.
- Its UTC-day spending ledger.
- Pausing enrichment at the configured limit.
- Recording spend before a later database write can fail.

A platform-side spending ceiling could be a useful independent safety feature,
but it is not necessary to replace the current provider call.

### Cache and reprocessing policy

Recipe-search LRU behavior, nutrition cache versioning, and decisions about
re-enriching old records belong to Nutritext. Agent activation events or
version-aware cache helpers might be convenient, but are not transport gaps.

### Database provenance

Agntz should expose run and resolved-version metadata. Nutritext decides whether
to add columns and persist it alongside facets, nutrition parses, or social
recipes.

## Migration unlocked by each gap

| Agntz change | Nutritext calls unlocked |
|---|---|
| Full nested JSON Schema | Facets, nutrition residue, social extraction |
| Model/provider option forwarding | Correct behavior for existing hosted agents and social extraction |
| Hosted multimodal preservation | Social visual extraction |
| Audio/file or transcription support | Social narration transcription |
| Typed signed callback tools with trusted context | Hosted SMS nutritionist |
| Usage/model/version in sync results | Simple facet and social transport replacement |
| Caller-controlled retention | Operationally safe stateless enrichment and image-heavy social runs |
| Image generation and artifacts | Future generated-image agents |

## Suggested implementation order

### Phase 1: make text-to-JSON hosting reliable

1. Unify the manifest JSON Schema contract.
2. Forward common model settings correctly.
3. Return usage, model, run ID, and resolved agent version from synchronous
   calls.
4. Add provider-harness fixtures based on Nutritext's facet and nutrition
   schemas.

This phase should unlock recipe facet enrichment and ingredient residue parsing.

### Phase 2: support the prepared social-extraction input

1. Preserve ordered multimodal content blocks through hosted manifest
   execution.
2. Support OpenAI reasoning, verbosity, provider storage, and image detail.
3. Add trace-only or no-retention execution and avoid persisting raw frame
   bytes.

This phase should unlock visual recipe extraction while transcription remains a
direct call.

### Phase 3: add audio transport

1. Add uploaded artifacts or audio/file content blocks.
2. Add a transcription operation and provider adapter.
3. Define file ownership, expiry, limits, and retention.

This phase should remove the remaining direct OpenAI call from the social
pipeline.

### Phase 4: host the nutritionist safely

1. Add typed HTTP/callback tool schemas.
2. Pass model arguments into callback bodies.
3. Inject trusted runtime session context separately.
4. Sign requests and support idempotent delivery.

This phase should allow the current embedded nutritionist agent to move to
agntz.co while leaving its recipe and user business logic in Nutritext.

### Phase 5: future image generation

Add an image-generation operation, hosted artifact outputs, provider adapters,
and async lifecycle support when Nutritext has a concrete generation use case.

## Final compatibility target

Agntz is a complete replacement for the direct non-batch model requests when
Nutritext can do all of the following:

1. Publish each prompt, model, model setting, and structured schema as a hosted
   manifest.
2. Send the same text, structured input, images, or audio it sends today
   without provider-specific request construction.
3. Receive the same structured content, model identity, and usage information
   its surrounding business logic consumes today.
4. Let hosted agents call Nutritext tools with typed model arguments and trusted
   non-model identity.
5. Choose retention appropriate to conversational, stateless, and binary-heavy
   workloads.
6. Change agent behavior in Agntz without deploying Nutritext, provided the
   input/output application contract remains compatible.
